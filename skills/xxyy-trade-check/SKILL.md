# XXYY 交易核查

## 直接触发

- 用户独立发送交易哈希/签名或区块浏览器交易详情链接，即视为“帮我查这笔XXYY交易有没有错池、被夹等问题”，直接开始只读核查，无需再问“想查什么”。不要求用户输入 `$xxyy-trade-check`、XXYY字样或查询动词。
- 例如仅发送 `0x` 开头的64位十六进制交易哈希，或 BscScan、Etherscan、BaseScan、RH Scan、Solscan 等浏览器的交易链接。链接可附中文标点，规范化时只移除链接外的标点。
- 先验证是交易标识；不要把40位EVM地址、任意长字符串或其他任务引用的哈希直接当成交易。未知链先按下述流程识别，仍无法定位时才询问缺失信息。
- 默认同时检查错池及夹子线索，证据支持哪一种就报告哪一种；可以并存或都未证实。若交易实际并非XXYY发起，说明来源不一致，仍完成已授权的该笔核验，不把问题强行归责XXYY。
- 多个独立交易哈希按笔核查并汇总；用户明确只要某个结果时优先服从其范围。

以 XXYY 产品中的用户交易问题为入口：接收交易哈希、XXYY 页面/截图或钱包与合约信息，查清用户在 XXYY 看到的成交、池子、金额与余额，再用链上资金流和同期行情核验原因。只有哈希时，先识别链、钱包与合约以定位 XXYY 记录。问题来自 XXYY 不代表责任必然在 XXYY，区分产品显示/索引、执行路由、代币机制、MEV与市场变化，按证据归因。默认中文回复，结论、金额、证据在前。调查为只读，不签名、不授权代币、不提交兑换；报价模拟也须保持只读。

## 交付范围

- 单个哈希：调查该笔及证明原因所需的相邻交易，不默认审计整个钱包所有资产。
- “这个钱包在这个合约走了哪些池”：从哈希识别钱包和代币，检索该代币交易并逐笔核对收据。写明检索时间范围及分页完整性；“检出五笔”不能改写成“历史只有五笔”。
- 默认给出 XXYY 钱包筛选截图，红圈标注目标交易；用户只要简短结论或明确不需截图时从其要求。
- 默认必交付损失计算、可复算的计算逻辑和简明总结，不等待用户再次要求“算下损失”。分别报告异常执行差额、已核实费用及适用的持仓/已实现盈亏。未发现异常不等于交易无成本；无法确认损失也不能填成0。数据不足时仍交付已核实费用、可成立的估算区间及缺失数据，不制造完整金额。

## 1. 确认链、钱包与合约

1. 用户给浏览器链接时，以对应链的交易/收据确认；只有哈希时，结合本轮线索对少量合理候选链做并行只读查询。此前讨论过 BSC 不等于这次也是 BSC。
2. EVM 哈希格式不能确定链。RPC `null` 只表示该节点当时未找到，区分超时、限流、未同步、未上链及链不匹配。确认 RPC chainId，必要时交叉浏览器核验；候选查不到再问链名/完整链接，不遍历猜测所有网络。
3. 记录链/chainId、状态、区块号、transactionIndex、UTC 和北京时间（UTC+8）、发送者及接收合约。失败交易通常仅花 Gas，不能描述为已成交错池。
4. 区分发送者、实际付款人、代币收款人、智能账户、代付者、路由器和池子；中转合约不等于用户钱包。
5. 结合 Transfer/Swap、原生币内部转账、包装币 Deposit/Withdrawal、余额变化核对净资金流。读取目标合约、符号和 decimals，同名币不视为同一资产。不假设18位小数或10亿总量。

保留证据表：`chain | txHash | block/index | UTC/UTC8 | sender/payer/recipient | token | grossInput | netSwapInput | netReceived | feeTransfers | gas | swapHops`，注明单位、来源和价格时点。

## 2. 重建实际路由

- V2/V3：按每个 Swap 的发出地址、token0/token1、输入输出及储备/价格定位实际池。
- V4/Pancake Infinity：PoolManager/Vault 是共享合约，不是独立池。以 `bytes32 poolId` 配合 PoolKey/Initialize 识别币对、费率、hook；确认协议 ABI 后解码。
- 拆单逐段列出，区分直接买卖目标币的池与 BNB/USDT 等中转池。只有一个最终 Transfer 不代表只用了一个池。
- 按实际协议核验动态费、LP费、协议费、hook扣款及分母；不能看到 `fee=100900` 就跨协议套用10.09%。协议费可能已包含在 swap 总费中，禁止重复相加。
- 对照入池、出池及用户实收，识别路由费、代币税、退款和找零。不把同一资金的多次中转重复算成支出。

## 3. XXYY 大小池对照

1. 用户指定 Chrome 时使用 Chrome，以当前工具文档为操作依据。可用公开 RPC、浏览器或行情 API 交叉核验；正常只读重试不反复请求许可。
2. 用确认的链与合约搜索 XXYY，分别打开实际池与活跃对照池。合约直达失败时走站内搜索或已验证 Pool ID。出现 undefined、空K线、零持有人时，`$0` 先视为未加载/未索引候选状态，不能当归零证据。
3. **自动跳转的默认池不等于主池**。查多池结果，必要时用 Dexscreener 或链上池事件补足。记录完整池地址/ID、币对、协议、创建时间、活跃度、双边储备和流动性。
4. 大小是相对概念，不设固定美元阈值。主要看交易时的可执行深度、报价币储备、同额报价及同期成交。当前TVL仅标核查时快照；集中流动性不能用总TVL代替当前区间深度。
5. 不把异常池虚高币价乘库存所得“数十亿流动性”当真实深度，核对报价币储备与实际成交能力。
6. 对照池必须同链、同合约、在交易前已存在且可交易。核对报价资产价值、decimals、币对方向。
7. 实际池与活跃池不同且有明显可比报价劣势，才支持“错池/较差旁池”。唯一有效主池本身浅时应写“主池深度不足”。仅地址不同不能认定路由错误。

## 4. 夹子证据与原因分类

错池和夹子可以同时存在，不强制三选一。分别判断路由质量、MEV、费用和后续行情。

| 结论 | 所需证据 |
|---|---|
| 错池/较差旁池 | 实际Pool ID、可用对照池、交易时的深度或同期价格劣势 |
| 被夹（确认） | 前后相关操作哈希及区块顺序；先行操作使用户价格变差；后续反向操作/撤流动性获利；能证实同一控制方、资金闭环或明确关联，并说明因果及利润/反事实影响 |
| 疑似被夹 | 仅有部分结构，关联、获利或因果未验证，明确缺口 |
| 暂无夹子证据 | 已检查范围没有完整结构，不写“绝对没有被夹” |
| 其他原因 | 高费率、税、浅池冲击、买后下跌、撤流动性、卖出/转出、索引显示异常，各需独立证据 |

- 顺序用 block + transactionIndex + logIndex，不只用秒级时间或K线尖刺。
- 围绕实际池检查同区块前后交易，按需扩展相邻区块。浏览器“同一发送者上一笔/下一笔”不是区块相邻交易。
- 用户之后别的钱包卖出不足以证明被夹；单纯 backrun 套利不等于 sandwich。相近 Gas、同一路由合约、反向获利都不能单独证明同一控制方。
- 留意恶意建池、动态费调整、hook、临时增减流动性等机制。若不是经典前买后卖，描述已验证机制，不强行命名为夹子。
- 用户只问错池且证据充分时不扩展为全链MEV审计；明确问被夹时完成相应检查或报告未完成边界。

## 5. 默认输出：只给用户需要的结果

默认中文，使用以下顺序：一句结论 → 交易信息表 → 池子表 → XXYY截图 → 详细计算及亏损合计。用户明确缩小范围时只回答所问，不重复整份报告。

### 一句结论

`钱包[短地址]于[北京时间]在[链]买入/卖出[代币]；错池：[判断]，被夹：[判断]；本笔损失[金额/区间及口径]（[是否含路由费/Gas]）。`

- 错池使用“是 / 未发现 / 待确认”；被夹使用“已确认 / 疑似 / 暂无证据 / 未完成核验”。只有证据充分才写“是”或“已确认”，结论后至多一句关键依据。
- 同期价格估算直接标“错池损失参考（同期估值）”，历史模拟标“执行差额”，完整往返标“已实现净亏损”。不要在后续追问中把估算升级成确定损失。

### 交易信息表

必须包含：完整钱包地址、日期及时间到秒（默认北京时间UTC+8）、链、买入/卖出、代币名称/符号、完整代币合约、目标交易浏览器链接。付款人与收款人不同时分列；相同时只写一行钱包。多笔逐笔列出时间及哈希，不默认展开无关钱包历史。

### 池子表

使用 `角色 | 大/小池 | 协议及币对 | 完整池地址/Pool ID（XXYY链接） | 判定依据`。

- 明确列“主池/对照池”和“实际成交池”；确认错池时实际池标“错池”。实际就是主池时合并一行，不虚构错池。
- 每个池显式标“大池 / 小池 / 大小待确认”；不能把“主池=大池、错池=小池”当默认事实。若只有当前储备证据，写“大池（核查时）/小池（核查时）”，不要冒充交易时深度。
- 主池未确认时写“对照池（主池待确认）”。地址显示完整，V4用完整bytes32 Pool ID，不用PoolManager地址替代。依据只给关键同期报价、深度或储备及其时点。

### XXYY交易筛选截图

先读 [references/xxyy-evidence.md](references/xxyy-evidence.md)。默认内嵌实际池和主池/对照池截图，附可下载文件和对应XXYY链接。两者相同时可合并。

- 完整钱包+目标时间筛选，完整哈希匹配目标行，红圈标注。涉及损失计算的关联买卖或夹子交易也应覆盖；一张图能清楚涵盖时不重复贴图。
- 图注写池角色及大/小、目标时间；跨池记录须注明真实成交池，右侧当前储备须标截图时点。
- 截图不可得时只写具体缺口，不伪造，不用区块浏览器截图冒充XXYY筛选记录。

### 详细计算及亏损合计

先读 [references/loss-calculation.md](references/loss-calculation.md)。计算必须直接出现在回复里，不能只放附件，也不能等待用户再次要求。

1. 用表列每笔实际总支出、净入池、实收数量/净到账、路由费、池费/税、Gas，以及对照价格或模拟输出、价格时点与来源、历史换算汇率。
2. 每笔给可复算公式，代入真实数字；买入估值按“总支出+未计入Gas−实收数量×同期价格”计算，先统一币种。用高低价时展示区间计算。不要重复加已包含的费用。
3. 最后用一行写“亏损合计：[原生币] ≈ [美元/U]；区间[如适用]；[费用范围及口径]”。单笔就是该笔，多笔只合计同口径；错池、夹子、费用和后续跌价重叠时不相加。
4. 另有完整往返时单列已实现亏损，不混入错池估值合计；不能可靠归属本笔时不强行摊分。数据不足写“损失待定；已核实费用X；缺Y”，不填0。

### 精简规则

- 不写问候、能力介绍、调查流水账、重复结论、长篇概念科普或“需要的话我可以”。进度更新只说影响结论的新发现。
- 技术解码、完整中转路径、RPC失败过程、原始日志放证据附件；仅在影响结论时正文用一句说明。不要删掉用户要求的地址、截图、代入计算来换取简短。
- 口径限制集中在计算末尾一句，例如“同期估值，非精确改道损失；主池正常费用和冲击尚未扣除”。不要在开头、计算、结尾反复解释同一限制。
- 用户追问“所以是错池吗/约多少U”时，用1–3句回答已有结论和金额，保留必要口径标签即可；没有新证据不重跑调查，不提高证据强度。
- 不把旧案例的钱包、池地址、价格、费率或损失金额写成默认值。调查严谨度不因输出精简而降低。
